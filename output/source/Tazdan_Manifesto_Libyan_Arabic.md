## 1. الملخص التنفيذي

تزدان منصة مالية عربية أولاً، ما زالت قبل الإطلاق، ومبنية انطلاقاً من ليبيا. تجمع الشفرة الهوية، ومحافظ بعدة عملات، والصرف، والتحويلات الداخلية، وروابط المطالبة، وضمان تداول الأفراد، وأدوات الادخار، وحفظ الأصول الرقمية، ودفتر قيد مزدوج، ولوحة تشغيل. الموقع يوضح أن الخدمات المنظمة تعتمد على الموافقات والشركاء. لذلك يمكن إثبات وجود منتج تقني، لكن لا يمكن إثبات مؤسسة تحويل دولي مرخصة وعاملة.

الدليل: server/src/index.ts; server/prisma/schema.prisma; https://www.tazdan.com/

أقوى أصل تقني مثبت هو طبقة المحاسبة والرقابة: الدالة postLedger تشترط توازن القيود لكل عملة، وتكتبها داخل معاملة قاعدة البيانات، وتحدّث الأرصدة المقروءة؛ ويمكن للمطابقة وفحص سلامة الأموال إيقاف التداول عند وجود فرق. لكن مراجعة الشفرة وحدها لا تثبت أن كل حركة مالية تمر عبر هذه الآلية، ولا أن بيئة تشغيل فعلية اجتازت تدقيقاً مستقلاً.

الدليل: server/src/services/ledger/ledger.service.ts; server/src/services/ledger/reconcile.service.ts; server/src/services/ledger/fundIntegrity.service.ts

## 4. البنية التقنية

التصميم الحالي تطبيق خادم واحد مقسّم لوحدات، وليس مجموعة خدمات مستقلة. Express يربط مسارات المجالات، والمتحكمات تستدعي الخدمات وPrisma. PostgreSQL يخزن الحالة المالية. Redis يدعم التخزين المؤقت وتحديد الطلبات بحسب التهيئة، وSocket.IO للمراسلة المباشرة. تبدأ المجدولات والمطابقة داخل عملية الخادم. ملف الإنتاج يبيّن nginx والخادم والويب وRedis مع الاعتماد على PostgreSQL مُدار.

الدليل: server/src/index.ts; server/src/utils/redis.ts; docker-compose.prod.yml

**علاقات المكونات المثبتة**
Expo / Next.js → nginx / API → مجالات Express → Prisma / PostgreSQL → Redis وSocket.IO

|الطبقة|الآلية الحالية|
|---|---|
|الواجهات|هاتف Expo Router؛ ويب Next.js العام والإداري.|
|واجهة API|مسارات Express ووسائط وJWT وحدود طلبات ومتحكمات.|
|المال|خدمة دفتر، أرصدة قراءة، إيداع وسحب وصرف.|
|الحالة|Prisma/PostgreSQL؛ Redis اختياري؛ بعض حالة FX داخل العملية.|
|التشغيل|مطابقة وسلامة أموال وجاهزية ومجدولات وSentry عند التهيئة.|

الدليل: server/src/index.ts; server/src/services/ledger; server/src/services/ops/operationalReadiness.service.ts

## 6. الدفتر وحركة الأموال وحمايتها

تتوازن مجموعة القيود لكل عملة قبل اعتمادها: القيد الموجب يضيف لحساب، والسالب يخصم منه. حساب USER لا يسمح عادة برصيد سالب؛ وتمثل حسابات SYSTEM_ONRAMP وSYSTEM_OFFRAMP وSYSTEM_CHAIN وSYSTEM_FX وSYSTEM_ESCROW وPLATFORM أطراف الحركة أو وجهاتها الداخلية. تفحص المطابقة الرصيد المخزن في LedgerAccount مقابل القيود، وWallet نموذج قراءة للأصول المدعومة.

الدليل: server/src/services/ledger/ledger.service.ts; server/prisma/schema.prisma

**فئات الأموال**
حق العميل → حساب حماية لدى شريك → سيولة التسوية → مال تشغيل الشركة

**مثال تحويل داخلي: أحمد يرسل 1,000 دينار لمحمد**
حساب أحمد -1,000 → مجموعة LYD متوازنة → حساب محمد +1,000

|قيد توضيحي|مدين / سالب|دائن / موجب|التحقق|
|---|---|---|---|
|تحويل داخلي|أحمد USER LYD 1,000|محمد USER LYD 1,000|صافي LYD = 0|
|رسم توضيحي|أحمد USER LYD 3|PLATFORM LYD 3|صافي LYD = 0|
|إيداع خارجي|SYSTEM_ONRAMP LYD 1,000|أحمد USER LYD 1,000|يلزم مطابقته مع المصرف|

الدليل: server/src/services/ledger/ledger.service.ts

توازن الدفتر الداخلي شرط مهم لكنه لا يحمي أموال العميل وحده. على الشريك المرخص تحديد صاحب الحساب قانوناً، وفصل أموال العملاء عن السيولة التشغيلية وأموال الشركة حيث يفرض القانون، ومطابقة كشف المصرف أو الحفظ مع الدفتر يومياً، وتحديد تغطية العجز والتعامل مع التعثر ومن يتحمل خطر الطرف المقابل. لم تثبت هذه الترتيبات بعقود أو كشوف مصرفية.

الدليل: server/src/services/ledger/reconcile.service.ts; https://www.tazdan.com/trust

## 7. الحوالات الدولية: نموذج التشغيل المستهدف

المسار الصادر القابل للتنفيذ يبدأ بشريك ليبي مرخص يستلم الدينار؛ وتسجل تزدان الالتزام؛ ثم يسبق عرض السعر الملزم فحص الهوية ونشاط الشركة والعقوبات والأشخاص السياسيين ومصدر الأموال وغرض الدفع؛ وبعدها يحول شريك تسوية مرخص القيمة وينقلها، ويدفع شريك مرخص في بريطانيا أو غيرها للمستفيد؛ وتُطابق الجهتان وتُحال الاستثناءات للمشغّل. المسار العكسي يحتاج جامع أموال مرخصاً في بلد المرسل وشريك دفع قانونياً في ليبيا. هذا لا يثبت وجود عقود تشغيل لهذه الممرات حالياً.

الدليل: PROPOSAL; server/src/routes/transfer.ts; server/src/routes/claimLink.ts; https://www.tazdan.com/

**حالات الحوالة الصادرة المقترحة**
مسودة → مفحوصة → سعر → ممولة → موجهة → مسواة → مدفوعة → مطابقة

مثال مقترح: محمد في طرابلس يرسل 1,000 جنيه لابنته في مانشستر. عند سعر توضيحي 12 ديناراً للجنيه، التمويل 12,000 دينار إضافة إلى رسم معلن؛ ويجب أن يحدد العرض مبلغ المستفيد وصلاحيته والمسار. بعد الفحوص يؤكد الشريك المحلي وصول المال، وينقل الدفتر الالتزام من التمويل إلى التسوية، ويوفر شريك الصرف الجنيه، ويؤكد شريك الدفع البريطاني وصوله للمستفيد. تُطابق أموال الدينار وتسوية الجنيه ورسوم الشركاء والدفع النهائي. لا يُعد المسار مكتملاً لمجرد إمكان مطالبة رابط داخل تزدان.

الدليل: PROPOSAL; server/src/routes/claimLink.ts; server/src/routes/transfer.ts

في المثال العكسي يمول مرسل في لندن 500 جنيه لدى مشغّل بريطاني مرخص. بعد فحص الهوية والمستفيد، يحول الالتزام بسعر معلن، ويدفع شريك ليبي مرخص للأم في طرابلس بالدينار عبر وسيلة مؤهلة. يلزم تصميم أسباب الرفض وبيانات المستفيد الخاطئة وانتهاء العرض وتطابق العقوبات ومسؤولية رد المبلغ قبل الإطلاق. الممرات المرشحة تشمل بريطانيا ومصر وتركيا وإيطاليا/الاتحاد الأوروبي والإمارات وتونس، حسب الجدوى القانونية والشركاء.

الدليل: PROPOSAL

## 8. الكيانات والشركاء وبنية التسوية

الدليل: PROPOSAL; https://www.tazdan.com/partners; server/src/utils/seed.ts

## 9. اختيار المسار والسيولة والخزينة

محرك اختيار المسار المستقبلي يستبعد أولاً كل مسار غير قانوني أو غير متاح، ثم يرتب الباقي حسب صافي ما يصل للمستفيد والسيولة وحدود الشريك ووقت التسليم واحتمال الفشل وكلفة الصرف والدفع ومواعيد المصارف والتعرض أثناء التسوية. المسار الرخيص بلا سيولة دفع لا يمكن تنفيذه. الشفرة الحالية فيها تسعير صرف وموصلات مزودين، لكن لم يثبت محرك ممرات دولية كامل.

الدليل: PROPOSAL; server/src/services/exchange/priceEngine.service.ts; server/src/services/exchange/fxRateProvider.service.ts
